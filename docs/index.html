A drone that re-learns its own dynamics after every flight

The flight controller is a model predictive controller. Its model isn't hand-derived; it's identified from the drone's own flight logs with PySINDy. That identification runs again after every flight, so as motors wear and sensors drift, the controller's picture of the drone moves with them.

How it works

The challenge

The hackathon simulator streamed the drone's position at 10 Hz over gRPC and accepted three integer commands back: throttle, roll and pitch. The goal was to fly into a target region inside a bounded arena without crashing. Nobody tells you the drone's equations of motion, so you either hand-tune a PID controller or you learn a model.

The loop

Every flight produces a log of states and inputs. After the flight, PySINDy fits a sparse model of the dynamics from that log. The MPC loads the new model for the next flight. Repeat.

Step 1 · System identification with SINDy

SINDy (Sparse Identification of Nonlinear Dynamics) assumes the dynamics are a sparse combination of candidate functions of the state and input:

ẋ = Ξ⊤ θ(x, u)

θ is a library of candidate terms and Ξ the coefficients. Derivatives are estimated from the logged positions by finite differences, then sequentially thresholded least squares (STLSQ) repeatedly solves the regression and zeroes out small coefficients, so you're left with only the terms the data actually supports. With an identity library, the result is a linear state-space model you can hand straight to a controller:

ẋ = A x + B u   →   xk+1 = Ad xk + Bd uk

The fitted continuous model is discretised at the 100 ms control period (zero-order hold) before going into the MPC.

Step 2 · Model predictive control

At every tick the MPC predicts the next N steps with the identified model, then solves a quadratic program for the input sequence that minimises tracking error and control effort while respecting actuator limits:

minu Σk ‖xk − r‖²Q + ‖uk − uss‖²R + ‖xN − r‖²P
s.t.   xk+1 = Adxk + Bduk,   umin ≤ uk ≤ umax

Only the first input is applied; next tick it re-plans from the new measurement (receding horizon). The cyan line in the demo is that plan. Because the prediction comes from the identified model, the controller is only as good as the model.

Step 3 · Why refit after every flight

Real drones don't stay the same. Batteries and motors lose thrust, the IMU's notion of "level" creeps, props get chipped. A model identified once at the factory slowly becomes wrong, and an MPC with a wrong model plans with the wrong gains and the wrong hover point. Re-running identification on every flight log keeps the model matched to the drone you actually have, with no manual retuning.

In the demo the hidden "real" drone loses about 3.5% of its thrust per flight and its IMU picks up roll/pitch bias. Try this:

  1. Turn off the disturbance estimator so the MPC relies purely on its model.
  2. Turn off refitting and let the tour run for a few flights. The drone starts settling short of its targets and the error bars grow.
  3. Turn refitting back on. After a flight or two the model catches up and the drone lands on target again.

Hackathon code vs. this demo

The demo re-implements the same pipeline in plain JavaScript so it can run as a static page. Some differences:

  • State. The hackathon model used position only (3 states, ẋ = Ax + Bu straight from the server's position stream). The demo adds velocity (6 states, still estimated from positions) so that wind and thrust show up as accelerations.
  • Library. A constant term is added (it absorbs gravity, mean wind and IMU bias), and a coefficient mask encodes two physical priors: no dependence on absolute position, and drag only on each axis' own velocity.
  • Safe refits. Each refit is regularised towards the previous model and only swapped in if it predicts a held-out slice of the flight better. Closed-loop data is poorly excited, and this stops one bad flight from producing a bad model.
  • Solver. The Python version builds condensed prediction and constraint matrices and solves with quadprog (including state constraints and a Lyapunov terminal cost). The browser version uses an accelerated projected-gradient solver with input bounds.
  • Wind. The demo adds an offset-free disturbance estimator, so gusts are rejected even before the model has learned the mean wind.

The browser core runs headless too: node docs/test/core.test.mjs checks that identification recovers the true gains and that refitting beats a frozen model under drift.
